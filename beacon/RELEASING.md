# Beacon Python Release Process

The main `beacon-otel` package and the optional `beacon-profiling` package are released under the same product version. Installation examples inherited from upstream or the historical `gtrace` package are not evidence of a Beacon release. Refer to actual release tags in the [product repository](https://github.com/beacon-observability/beacon).

The public product name is Beacon Python and the command entry point is `beacon`; the `gtrace` command must not be restored or released. Distribution package names are `beacon-otel` and `beacon-profiling`. The legacy `gtrace` name is used only for historical branches and source provenance. The [`beacon`](https://pypi.org/project/beacon/) and [`beacon-python`](https://pypi.org/project/beacon-python/) names on public PyPI already belong to other projects and cannot be used as distribution names for this project.

## Version Source

- [version.properties](version.properties) is the only manually maintained source for the Beacon Python product version. Development versions use `X.Y.Z.devN`, release candidates use `X.Y.ZrcN`, and stable releases use `X.Y.Z`. Stable release tags use `beacon-vX.Y.Z`, with `rcN` appended for release candidates; upstream `v*` tags are not reused. Both Beacon packages use this product version, while upstream package versions are not replaced in bulk with the Beacon version.
- After changing the product version, run `python beacon/scripts/check-version.py --sync` to copy it into both packages and synchronize the exact `beacon-otel[profiling]` dependency version. Run the check without `--sync` during routine development and before releases to detect divergence. Package-level version files are generated copies, not a second manually maintained version source.
- [upstream.lock.json](upstream.lock.json) records the tag and full commit for both Contrib and Core. The root [pyproject.toml](../pyproject.toml), [uv.lock](../uv.lock), and profiling dependencies are the actual build configuration. `check-version.py` verifies that this configuration matches the baseline record. Product and upstream versions remain independent. Follow the [synchronization process](UPSTREAM.md) for baseline upgrades.
- After building candidate wheels, pass each wheel separately with `--wheel` to verify its name, version, and four pinned OTel dependencies. Add `--tag beacon-vX.Y.Z[rcN]` when checking a release-candidate or stable tag. Development versions cannot pass a release-tag check. This check does not replace building sdists from the same source commit, functional testing, or runtime and DataKit acceptance, and it does not mean that the current development version is approved for release.

## Release Procedure

1. After completing backend and environment acceptance, confirm the candidate version in `version.properties`, run `python beacon/scripts/check-version.py --sync`, verify the lockfile, and commit the changes. The CI workflow in [ci.yml](../.github/workflows/ci.yml) installs both built artifacts in clean Python 3.10–3.14 environments, checks their metadata, and tests first-party packages. Confirm that CI passes for the commit before release.
2. Repository administrators create two GitHub environments, `pypi-profiling` and `pypi`, both restricted to `beacon-v*` tags and protected by manual review. On PyPI, configure Trusted Publishers for `beacon-profiling` and `beacon-otel`, both pointing to `beacon-observability/beacon-python` and `beacon-release.yml`, but using `pypi-profiling` and `pypi` as their respective environments. PyPI rejects the same repository, workflow, and environment combination for two pending projects with different names, so the first release uses separate environments. Reevaluate consolidation after the projects have been created. Set the repository variable `BEACON_PYPI_RELEASE_ENABLED` to `true` only after confirming that these protections are active. Without these settings, the [release workflow](../.github/workflows/beacon-release.yml) skips publishing and does not attempt an upload. Never store PyPI tokens in the repository.
3. Only after acceptance passes, tag the verified commit with `beacon-vX.Y.ZrcN` (or the stable version) and push the tag. Manually run `Publish Beacon Python` for that tag. After builds and tests pass, publish the profiling package first and then the main package. The release jobs wait for approval in the protected `pypi-profiling` and `pypi` environments, respectively. PyPI does not allow overwriting an existing version; increment the version after a failure instead of re-uploading published files.
4. After both PyPI packages are published successfully, the workflow automatically creates a GitHub Release and attaches the wheel and sdist for each package. Release candidates are automatically marked as pre-releases, while stable versions participate in GitHub's Latest release selection. A retried job reuses an existing release and replaces attachments with matching names. Review the generated release notes and add the corresponding Contrib/Core baseline, validated capabilities and environments, limitations, and rollback instructions.
5. Verify both package versions and artifacts on PyPI. Then install `beacon-otel[profiling,requests]` from the public index in a clean virtual environment and validate `beacon --version`, application auto-instrumentation, and ingestion by the target DataKit. Finally, update the Python entry point in the product repository.

The GitHub `pypi` and `pypi-profiling` environments have been created, restricted to `beacon-v*` tags, and configured to require manual review by `lrwh`. PyPI Trusted Publishers point to `beacon-observability/beacon-python`; `0.1.0rc1`, `0.1.0rc2`, `0.1.0`, `1.0.0`, and `1.0.1` were released through this process. `BEACON_PYPI_RELEASE_ENABLED` remains disabled during routine development and is enabled temporarily only during a manual release window. Neither code pushes nor development artifact builds in this repository publish automatically.

Before a stable release, define and validate the following in this repository:

1. Confirm the functional boundaries and stable versions of `beacon-otel` and `beacon-profiling`, along with any migration guidance for legacy packages. The stable `0.1.0` release is based on the accepted `0.1.0rc2` functional baseline. Conflicting profiling distributions cannot coexist with Beacon Profiling, and existing artifacts from other projects must not be overwritten.
2. Pin the Contrib, Python Core, third-party dependency, and license sources. Build candidate artifacts from the pinned commit and record their digests.
3. Record validation results for first-party functionality, upstream impact, Python runtime environments, DataKit backends, upgrades, and rollbacks. Bind the evidence to the same commit and artifacts.
4. Define release permissions, the target repository or package index, release approval, and rollback procedures. Do not enable inherited OpenTelemetry release workflows to publish Beacon.
5. Maintain release notes, known limitations, and versioned usage documentation for every version. After release, update the Python installation and release entry points in the product repository.

Each language is released independently. Beacon Python does not need to stay in lockstep with Beacon Java or Go, and passing local tests does not constitute release acceptance.
