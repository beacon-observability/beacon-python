# Beacon Python 0.1.0 Stable Release Acceptance Record

## Conclusion

`beacon-otel==0.1.0` and `beacon-profiling==0.1.0` use the functionality and backend acceptance completed for `0.1.0rc2` as their baseline. Before the stable release, version consistency, code formatting, artifact builds, artifact metadata, post-installation tests, and Python 3.10–3.14 CI were run again. After release, clean installation and startup were validated from public PyPI.

## Functional Baseline

- OpenTelemetry Python Contrib: `v0.65b0`
- OpenTelemetry Python Core: `v1.44.0`
- Supported Python versions: 3.10–3.14
- Traces: standard OpenTelemetry auto-instrumentation and OTLP export
- Profiles: CPU Time, Wall Time, Heap Live Size, lock-contention collection, and handled-exception collection
- Default profile export interval: 60 seconds, configurable through an environment variable or constructor argument

DataKit trace and compatible pprof ingestion, profile value semantics, the default export interval, the FastAPI demo, and trace/profile correlation were accepted in `0.1.0rc2`; see [`0.1.0rc2.md`](0.1.0rc2.md) for evidence. The stable release introduces no runtime functionality changes relative to that release candidate.

## Known Limitations

- The current DataKit ingestion path uses compatible pprof rather than OTLP Profiles v1development.
- `tracemalloc` has noticeable overhead with many small objects and very short memory snapshot intervals. The default interval is 60 seconds and can be adjusted through an environment variable or constructor argument.
- After OpenTelemetry resource attributes enter DataKit, they are normalized according to the DataKit trace field model. Non-built-in tags may be retained in extended attributes.
- Do not install another profiling distribution with a conflicting auto-instrumentation entry point in the same Python environment.
