# Beacon Python 1.2.0 Public Release Acceptance

Date: 2026-10-20.

The stable `v1.2.0` tag resolves to `ff40fa9a6faeb9cd47262d2c3c3ed8b6944d7a71`. Both `beacon-otel` and `beacon-profiling` use version `1.2.0`. Security remains embedded in `beacon-otel` and disabled by default.

## Source and Build Evidence

- [Merged release PR #21](https://github.com/beacon-observability/beacon-python/pull/21) brings the attack-evidence implementation onto main; its original stacked PR #20 had been merged into the prerequisite feature branch.
- [Source CI](https://github.com/beacon-observability/beacon-python/actions/runs/39366272830) passed CPython 3.10–3.14, building and testing installed wheels. The 132-test Security suite ran on supported standard-GIL CPython 3.11–3.14; CPython 3.10 received schema and package validation.
- [Release workflow](https://github.com/beacon-observability/beacon-python/actions/runs/39366512983) built and tested the exact wheel and sdist artifacts. Both protected publishing environments retained tag restrictions and reviewer protection. Profiling was published before the main package; the release variable was restored to `false` afterwards.
- Contrib: `v0.65b0`, `a5470c666947acddc24fd4064ec7c1b169dfe8b6`; Core: `v1.44.0`, `53a5a40c9604583c501bcf13970a635f00e62df4`.

## Public Artifact Acceptance

A new CPython 3.12.3 environment installed the exact public `beacon-otel[profiling,flask,requests]==1.2.0` distribution from PyPI without repository sources. Installed package versions and `beacon --version` both matched `1.2.0`. The public wheels and sdists matched the accepted release artifact SHA-256 digests.

An application module with no telemetry imports was launched through the public `beacon` command. A local OTLP HTTP/protobuf receiver verified application trace and Security records; a compatible pprof endpoint verified profiling uploads.

- Default Security configuration: three Flask requests produced application spans, no Security runtime or threads, no Security findings, and no local Security output.
- Explicitly enabled Security: three requests through the same native SQLite dynamic-template sink each produced a finding with the same finding ID, distinct occurrence/evidence IDs, current trace context, and process-local counts `1, 2, 3`.
- The request fragments `12`, `1 OR 1=1`, and `14` produced `no_evidence`, `suspected`, and `no_evidence` respectively with ANSI analysis explicitly configured. Evidence sampling was `true`, `true`, `false`: the stronger second request bypassed the detail interval, and the final ordinary request retained its own classification.
- A runtime-SBOM snapshot and compatible pprof uploads reached the receiver. Security local output remained absent.

## Boundaries and Rollback

Security requires an explicit application include prefix and standard-GIL CPython 3.11–3.14. Unsupported SQL/shell syntax, imprecise evidence, and missing network/path policy remain unknown. Attack evidence is independent of risk assessment and does not establish exploit success. Counters are process-local and delivery remains bounded best effort; trace presence is not guaranteed by its ID.

This is local protocol acceptance, not a new DataKit backend qualification. Gunicorn requires `preload_app=False`; profiling uses compatible pprof rather than the OpenTelemetry Profiles signal. See the version-pinned package README for configuration.

To roll back, install `beacon-otel[profiling,flask,requests]==1.1.0` in a clean environment. Existing published artifacts and tags are immutable.
